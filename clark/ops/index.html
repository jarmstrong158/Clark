Opening assignment for a single day

Pick a facility and date. Returns Clark's recommended task assignment for every worker on that shift.
How to read this
What you get
  • Worker — name from the facility config
  • Task — what Clark wants them doing at shift start (pick, pack, restock, management, idle, etc.). absent = called off / forced out
  • Hustle — yes means hard pace; no means normal pace. Hustle is a real cost Clark pays only when needed
Scope (honest)
  • This is an opening assignment — what Clark would do at 9 AM. It's not a simulated end-of-day result. For projected outcomes, use Sweep
  • Volume override lets you ask "what if today's volume is 400 instead of the season-sampled value?" Leave blank for normal
  • Seed makes the plan reproducible. Same seed → same plan, exactly

Base vs. modified plan side-by-side

Compare two plans for the same facility + date. The "modified" run absents specific workers and/or overrides volume; the "base" is what would happen with nothing changed.
How to read this
What you get
  • One row per worker; columns: Base task / Base hustle vs Mod task / Mod hustle
  • Rows that actually changed are highlighted green. If nothing's highlighted, your modification had no effect on the plan (Clark re-routed around it without disruption — or your worker name didn't match)
  • An explicit ⚠ warning appears at the top when base==modified — usually means a typo in the absence list or volume already at the regime boundary
How it differs from chaining two Plans
  • Both runs share a deterministic seed, so they differ only by your modification. No episode-noise pollution
  • Absences are deterministic here — not subject to the random call-off roll Plan uses
What it doesn't tell you
  • It's still opening-assignment, not a simulated end-of-day result. "Worker D is out, plan looks identical" doesn't mean the day will finish identically — Clark might just delay the impact

Cross-facility tightness ranking

Plan N facilities for the same date in one shot and rank them. Use to answer "of my warehouses, where am I shortest on Monday?".
How to read this
The tightness formula
  • tightness = hustling − (active workers NOT hustling)
  • Positive = more workers hustling than coasting → stretched, short-staffed for the day's volume
  • Negative = plenty of slack → over-staffed for the day
  • Zero = balanced
The ranking
  • Sorted highest tightness first. Top row = where to send a temp worker
  • The Model column shows whether each facility used its own fine-tuned weights (fine-tuned) or the generic foundation (foundation). Fine-tuned facilities often show lower tightness because the policy learned how to ship the day with less hustle
What it doesn't tell you
  • Absent is always 0 here — this is a clean roster snapshot, not a what-if. For absences, use the What-if tab
  • It's opening-assignment per facility, not an end-of-day outcome. A high-tightness facility might still finish cleanly; a low-tightness one can still F if something breaks. For projected outcomes use Sweep

Staffing-sufficiency sweep

Run the trained policy through many simulated days at different roster sizes. Returns the daily-grade distribution at each step. Use to answer "would hiring 2 more workers actually help?".
How to read this
The bars
  • One stacked bar per roster step (e.g. +0, +1, +2 extras over the base roster)
  • Each bar shows the daily-grade mix: A = ship-clean + management OK, B = ship-clean with minor demerits, C / D / F = increasingly bad days (F = orders missed)
  • You want the green band as wide as possible and the F slice as narrow as possible
How to use the result
  • If the bars are roughly identical across roster sizes, you're past the elbow — hiring more won't help (capacity is bottlenecked elsewhere)
  • If +1 worker dramatically increases A and shrinks F, that's your minimum viable roster
  • The smallest extras count where the grade mix plateaus is the cheapest "sufficient" answer
Scope
  • This is a real end-to-end simulation, not a snapshot. Each bar is N days of actual sim → real outcome distribution on the days run
  • Slow on purpose. Defaults to 40 days/step × 5 steps = 200 days. Bump to 261 (full year) for tightest stats; drop to 20 for quick sanity checks

Workday sanity check

Verify a date is actually a workday for a facility before planning it. Refuses to silently plan a fake Saturday on a Mon-Fri site.
How to read this
What you get
  • Workday badge: green = real workday, orange = not (Sunday, or Saturday on a Mon-Fri facility)
  • Weekday + month + flags like peak month (the facility's configured peak-staffing window)
  • A summary sentence the chat would quote verbatim to a user
When to use it
  • Before planning a date that "feels wrong" — Saturday for a 5-day facility, a holiday, an off-calendar month
  • To check whether a facility's configured peak season is in effect for a given date (extra workers will be in the model that day)

Training runs

Live progress for every fine-tune detected on disk, auto-refreshing every 5 seconds. One card per run; bar shows percent complete + ETA.
How to read this
Status pill
  • running (green border) — heartbeat seen within the last 2 minutes
  • complete (blue border) — finished cleanly; total time shown
  • stopped (red border) — heartbeat went stale without finishing. Either killed mid-run, crashed, or the trainer is paused
The numbers
  • ETA is linear extrapolation: (elapsed / current_episode) × (target − current). Reasonable for steady-rate training; can be off if the per-episode time changes (warmup, GPU contention)
  • Elapsed is wall-clock since the run started, not including time the process was killed and restarted
  • Last avg reward is the most recent episode's average reward — only shown if the trainer reports it (foundation has none; fine-tunes do)
Where the data comes from
  • Scanned from clark/data/checkpoints/user/logs_*/training_metrics.json + the foundation's pretrain dir
  • Polling pauses when you leave this tab — no background network from other tabs

Morning briefing — all facilities

A one-page snapshot for the day: for every facility, calendar-check the date, pull the plan, flag risk. Ranked most-at-risk first.
How to read this
Per-facility card
  • ⚠ (orange border) = at least one risk flag fired. • (grey) = quiet day. — (dim) = not a workday for this facility
  • active / hustling / absent = headcount snapshot
  • peak month badge appears for facilities in their configured peak-staffing window on this date
Risk heuristics
  • >50% of active workers hustling — schedule is tight
  • >25% of roster absent — short-handed
  • Any calendar flag passes through (e.g. Saturday on a Mon-Fri site)
Notes
  • Same heuristics as the clark-mcp-briefing CLI — run that from a cron job for an automated morning email
  • "Flagged" doesn't mean "the day will fail" — just "look at this one first"
